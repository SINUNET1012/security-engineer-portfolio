1. 프로젝트 개요 [상세 문서]

3차 퍼플팀 프로젝트는 "로그를 모아 보기"에서 끝나는 것이 아니라, "로그 기반으로 공격을 탐지하고 자동 대응까지 연결하는 실습형 SOC 파이프라인"을 만드는 것이 핵심입니다.[1]

한 줄 정의

수집 -> 정규화 -> 탐지 -> 검증 -> 대응 -> 증적 기록의 반복 루프를 실습 환경에서 재현하고 운영 가능 상태로 만드는 프로젝트[2]

2026-01-21 ~ 2026-01-26 3차 구조 정리 및 일정 확정 로그 수집 -> 탐지 -> 자동 대응 프레임 고정
2026-02-01 ~ 2026-02-10 룰 작성/보강 및 자동화 정리 구축 중심에서 운영/인수인계 중심으로 전환

2. 목표와 범위 [상세 문서]

핵심 목표

  1. 공격 이벤트를 로그로 빠짐없이 수집한다
  2. 탐지 룰을 근거 기반(Nessus/실제 로그/패킷)으로 작성한다
  3. 탐지 결과를 대시보드에서 검증 가능한 형태로 시각화한다
  4. 반복 공격에 대해 안전한 자동 대응 루프를 구성한다
  5. 팀원 전체가 개념 설명과 재구축이 가능한 상태를 만든다

범위/주의사항

  1. 프로젝트는 교육용 실습 환경에서만 수행한다
  2. 자동 차단은 화이트리스트/롤백 정책 없이 운영하지 않는다
  3. SOC/C&C 등 핵심 인프라는 공격 시연 대상에서 분리한다
  4. 탐지 룰은 오탐/미탐 검증 절차를 거쳐 단계 적용한다
  5. 발표용 시나리오는 재현 가능성과 증적 확보를 우선한다

3. 전체 아키텍처 흐름 [상세 문서]

1) 로그 생성서버, 네트워크 장비, 엔드포인트, 보안 장비에서 이벤트 발생
2) 로그 수집Beats/Syslog로 이벤트 전달
3) 로그 가공Logstash에서 파싱/정규화/필드화
4) 저장/검색Elasticsearch 인덱싱 후 Kibana에서 조회
5) 탐지Suricata/ModSecurity/Wazuh 룰과 상관 분석
6) 판단심각도, 자산 중요도, 반복 여부 기준으로 조치 결정
7) 자동 대응Ansible/방화벽 정책으로 차단 또는 격리
8) 증적 기록탐지 근거, 차단 결과, 롤백 여부를 문서/로그에 남김

4. 프로젝트 세부 흐름 [상세 문서]

단계 핵심 작업 산출물 완료 기준
Phase 0. 요구사항 정렬 팀 역할/로그 범위/공격 시나리오/차단 지점 합의 회의록, 요청서, 인벤토리 표 누가/무엇을/언제 제공하는지 문서화
Phase 1. 수집 기반 구축 ELK 스택 구축, 입력 경로 연결, 시간 동기화 서비스 상태, 인덱스 생성 확인 Kibana에서 원본 이벤트 조회 가능
Phase 2. 파싱/정규화 필드 추출(source.ip, event.action 등), 타입 정리 Logstash 파이프라인, 필드 표준안 대시보드 집계가 필드 기반으로 정상 동작
Phase 3. 탐지 룰 작성 Nessus/실공격 로그 기반 룰 작성 및 보완 Suricata/ModSecurity/Wazuh 룰셋 시나리오 재현 시 경보 발생
Phase 4. 자동 대응 연결 탐지 이벤트를 차단 정책으로 연결, 안전장치 적용 Ansible 플레이북, 차단 로그 자동 차단 + 롤백 절차 검증 완료
Phase 5. 운영/발표 정리 증적 캡처, 역할 인수인계, 재현 리허설 매뉴얼, 발표 자료, 운영 체크리스트 팀원 전원이 개념/구축 흐름 설명 가능

5. 기술 개념 백과 [상세 문서]

기술 개념 프로젝트 내 역할 입력/출력 포인트 운영 체크포인트
Filebeat / Syslog 로그 수집 에이전트/전송 계층 원천 로그를 Logstash 또는 Elasticsearch로 안정 전달 입력: 시스템/서비스 로그, 출력: 이벤트 스트림 누락률, 전송 지연, 재시도 설정
Logstash 수집된 로그를 파싱/정규화하는 ETL 계층 비정형 로그를 분석 가능한 필드로 가공 입력: beats/syslog, 출력: elasticsearch index grok 실패율, 파이프라인 병목, @timestamp 정합성
Elasticsearch 검색/집계 최적화 데이터 저장소 탐지 근거와 운영 로그를 인덱싱하여 조회 기반 제공 입력: 정규화 이벤트, 출력: 검색/집계 결과 인덱스 매핑, 보존 정책, 샤드/리소스 관리
Kibana 시각화/탐색 대시보드 경보 검증, 추세 분석, 발표용 증적 화면 제공 입력: Elasticsearch 인덱스, 출력: 시각화/쿼리 대시보드 표준화, 시간대 설정, 필터 재사용성
Suricata NIDS/IPS 엔진 네트워크 구간 공격 시그니처 탐지 입력: 패킷/트래픽, 출력: alert/eve.json 룰 업데이트, SID 충돌, 성능 튜닝
ModSecurity WAF 룰 기반 HTTP 요청 검사 웹 공격(SQLi/XSS/Traversal 등) 탐지 및 차단 후보 입력: HTTP 요청/응답, 출력: 감사 로그 DetectionOnly에서 시작, 오탐 분석 후 강제 차단
Wazuh + Auditd HIDS/호스트 로그 분석 계층 암호화 트래픽 이후의 시스템 내부 행위 탐지 입력: 시스템/보안 로그, 출력: rule alert NIDS와 룰 중복/보완 관계 설계, 규칙 우선순위
Nessus 취약점 스캐너 공격 시나리오/탐지 룰 근거 생성 입력: 대상 자산, 출력: 취약점/시도 로그 스캔 시간표 합의, 정상 트래픽과 구분
Ansible 구성/운영 자동화 도구 ELK 구축 반복 작업과 대응 정책 적용 자동화 입력: inventory/playbook, 출력: 원격 설정 변경 idempotency, 롤백 playbook, 실행 이력 기록
pfSense 경계 네트워크 제어 장비 차단 정책 반영 지점, ACL/규칙 적용 대상 입력: 정책 명령, 출력: 네트워크 제어 상태 config.xml 백업, 캐시 반영, 안전한 반영 절차
CAPE 악성코드 동적 분석 샌드박스 악성행위 분석 로그/보고서 수집 실습 입력: 샘플 파일, 출력: 분석 결과/행위 로그 가상화 의존성, 에이전트 통신, 타임아웃 관리
GNS3 / OSPF / IPv6 네트워크 토폴로지/라우팅 실습 환경 네트워크 동작 이해 및 공격 경로/로그 맥락 강화 입력: 라우터 설정, 출력: 라우팅/트래픽 결과 토폴로지 재현성, 설정 백업, 패킷 캡처 정합성

6. 데이터 필드 표준 [상세 문서]

탐지 품질은 로그 \"양\"보다 필드 \"품질\"에 더 크게 좌우됩니다. 아래 필드는 최소 공통 스키마로 관리합니다.

필드명 예시 출처 활용 목적 검증 규칙
@timestamp 2026-02-10T14:55:08Z 모든 로그 소스 타임라인/상관분석 기준 시간 NTP 동기화, 시간대 통일(UTC 또는 KST)
source.ip 192.168.10.25 웹, SSH, IDS, 방화벽 공격자 식별, 차단 대상 결정 사설/공인 대역 구분 태그 부여
destination.ip 10.10.2.14 네트워크/서버 로그 피해 자산 식별, 영향도 판단 자산 인벤토리와 매핑 가능해야 함
event.module wazuh / suricata / modsecurity 탐지 시스템 탐지 엔진 구분/정확도 분석 모듈명 표기 규칙 고정
event.action alert / block / login_failed 탐지 및 대응 로그 탐지와 대응 단계 분리 분석 동사형 네이밍 규칙 적용
rule.id 100103 Wazuh/Suricata/ModSecurity 룰 단위 효과 측정 및 튜닝 중복 ID 금지, 룰셋별 대역 분리
rule.level 7 / 12 / 15 탐지 룰 자동 대응 임계치 판단 레벨 기준서와 1:1 매핑
event.original 원문 로그 라인 수집 원본 오탐 분석, 감사 추적 원본 보관 기간 정책 준수

7. 공격-탐지-대응 시나리오 [상세 문서]

시나리오 관측 로그 탐지 지점 대응 액션 증적
Directory Traversal 웹 접근 로그의 ../../etc/passwd 패턴 ModSecurity/Wazuh 웹 룰 공격 IP 임시 차단, 룰 적중 로그 저장 Kibana 경보, WAF 감사 로그, 차단 이력
Log4Shell/JNDI 패턴 ${jndi:...} 문자열 포함 요청/로그 Wazuh 고위험 룰, WAF 룰 고위험 이벤트 즉시 알림 + 격리 후보 처리 경보 레벨, 원문 로그, 대응 승인 기록
SSH 스캐닝/Nessus 흔적 협상 실패, 비정상 서비스 요청, nessus 사용자 Wazuh SSH 룰 반복 IP 차단, 화이트리스트 예외 체크 탐지 카운트, 차단 전후 접속 로그
DNS AXFR/비인가 업데이트 AXFR started, update denied/failed named 로그 기반 Wazuh 룰 DNS 관련 포트 접근 정책 점검 DNS 로그 추적, 정책 변경 이력
RPC/NFS 비정상 요청 unknown version, bad TCP reclen 커널/RPC 로그 룰 스캐너 구분 후 네트워크 제어 강화 커널 로그, 탐지 타임라인

8. 운영 품질 KPI [상세 문서]

지표 정의 목표값(권장) 확인 주기 개선 액션
수집 성공률 발생 이벤트 대비 ELK 유입 비율 99% 이상 일 단위 에이전트/네트워크 재전송 정책 점검
정규화 성공률 파싱 실패 없이 필수 필드가 채워진 비율 95% 이상 일 단위 grok 패턴/필드 매핑 보완
탐지 적중률 재현 공격 시 경보 생성 비율 90% 이상 시나리오 테스트 시 룰 조건 보완, 로그 소스 추가
오탐률 정상 행위를 공격으로 판단한 비율 10% 이하 주 단위 예외룰/화이트리스트 정교화
평균 탐지 시간(MTTD) 공격 발생부터 경보 생성까지 걸린 시간 5분 이내 주 단위 수집 지연 구간 병목 제거
평균 대응 시간(MTTR) 경보 생성부터 차단/조치 완료까지 시간 15분 이내 주 단위 Runbook 단계 단순화, 자동화 범위 확대

9. 룰 설계 원칙 [상세 문서]

  1. 근거 우선: 룰은 실로그/패킷/스캔 결과 근거를 반드시 가진다
  2. 필드 우선: 문자열 검색만이 아니라 source.ip, uri, program_name 같은 구조화 필드 중심으로 작성한다
  3. 레벨 분리: 단순 스캔, 의심 행위, 확정 공격을 다른 심각도로 분리한다
  4. 오탐 관리: Detection 모드에서 검증 후 차단 모드로 승격한다
  5. 룰 생명주기: 생성 -> 검증 -> 적용 -> 모니터링 -> 폐기 기준을 문서화한다
  6. 상호보완: Suricata(NIDS)와 Wazuh(HIDS) 역할 충돌이 아니라 보완 구조로 설계한다

10. 자동화/안전장치 [상세 문서]

자동화 원칙

  1. 자동화는 재현 가능한 반복 작업부터 적용한다
  2. 인프라 구축 자동화와 대응 자동화를 분리해 관리한다
  3. 변경 전후 상태를 로그와 문서로 남긴다
  4. 운영팀이 이해 가능한 플레이북 구조를 유지한다

안전장치 체크

  1. 킬 스위치: 자동 차단 즉시 중지 가능한 절차 확보
  2. 화이트리스트: 관제/관리자/핵심 서버 예외 정책
  3. TTL 차단: 영구 차단 대신 일정 시간 후 해제 기본
  4. 롤백: 정책 실패 시 원복 플레이북 즉시 실행
  5. 승인 기준: 고위험 조치의 수동 승인 조건 명확화

11. 트러블슈팅 가이드 [상세 문서]

증상 가능 원인 1차 점검 2차 조치 재발 방지
Kibana에 로그가 안 보임 수집 중단, 인덱스 미생성, 시간대 불일치 에이전트 상태, Logstash 입력 포트, 인덱스 생성 여부 확인 파이프라인 재시작, 시간 동기화 재설정 수집 상태 알림/헬스체크 자동화
룰이 맞는데 경보가 안 뜸 필드명 불일치, 룰 순서/조건 충돌 event.original과 파싱 필드 대조, 룰 로딩 상태 확인 룰 조건 단순화 후 점진 확장 룰 테스트 케이스와 샘플 로그 저장
자동 차단이 과도하게 발생 오탐률 높은 룰, 예외 정책 누락 최근 차단 로그에서 정상 IP 비율 확인 임계치 상향, 수동승인 모드 임시 전환 화이트리스트/TTL 정책 표준화
Logstash CPU 급증 복잡한 grok, 단일 파이프라인 병목 파이프라인별 처리량, 실패율 확인 dissect/grok 분리, 파이프라인 다중화 파싱 규칙 정기 성능 점검
Wazuh/Suricata 경보 중복 동일 행위를 서로 다른 엔진이 동시 감지 rule.id, source.ip, timestamp 기준으로 중복 패턴 확인 상관분석 규칙 추가, 우선순위 재정의 엔진별 책임 범위 문서화

12. 운영/협업 체계 [상세 문서]

영역 협업 포인트 필수 산출물
서버팀 ↔ 퍼플팀 로그 위치/포맷/전송 방식/접근 권한 합의 로그 명세서, 수집 경로 표
네트워크팀 ↔ 퍼플팀 차단 지점(서버/경계), 방화벽 정책 반영 방식 합의 차단 정책서, 롤백 절차서
레드팀 ↔ 퍼플팀 시연 공격 타임라인, 재현 조건, 성공 기준 정렬 시나리오 스크립트, 검증 체크리스트
팀 내부 개념 공유, 매뉴얼 취합, 발표 메시지 통일 통합 매뉴얼, 발표 흐름도

13. 운영 Runbook [상세 문서]

주기 체크 항목 담당 기록 위치
매일 시작 전 ELK/Wazuh/Suricata 서비스 상태, 인덱스 유입 확인 퍼플팀 운영 담당 일일 점검표
매일 종료 전 고위험 경보 리뷰, 차단/해제 이력 정리 탐지/대응 담당 경보 리뷰 로그
주 1회 오탐/미탐 케이스 분석, 룰 성능 리포트 룰 관리 담당 룰 개선 회의록
주 1회 자동화 플레이북 드라이런 및 롤백 테스트 자동화 담당 플레이북 실행 이력
발표/시연 전 공격 시나리오 리허설, 증적 화면 캡처 재검증 전체 발표 리허설 체크리스트

14. 발표용 핵심 스토리 [상세 문서]

  1. 왜 필요했는가: 공격 로그는 쌓이지만 대응 루프가 없으면 운영 가치가 낮다
  2. 무엇을 만들었는가: 수집-탐지-자동대응을 하나의 흐름으로 연결했다
  3. 어떻게 검증했는가: Nessus/시나리오 공격으로 룰 적중과 차단을 반복 검증했다
  4. 무엇이 남았는가: 룰셋, 자동화 플레이북, 증적 대시보드, 운영 매뉴얼을 남겼다
  5. 다음 단계는 무엇인가: 오탐 관리 고도화, DB 연계 확대, 팀원 전원 재현성 강화

용어 의미

MITRE ATT&CK공격 전술/기술 분류 프레임워크. 룰 근거 설명에 활용

Runbook탐지 이후 조치 절차를 단계별로 정의한 운영 문서
